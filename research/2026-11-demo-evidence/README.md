# What Limbowatch finds that GitHub and OSV don't: evidence (November 2026)

**Question.** On a project with real lockfiles, does Limbowatch report anything that GitHub's Dependabot alerts and OSV-Scanner don't? And are those findings real?

**Answer.** Yes. On the [demo app](https://github.com/limbowatch/demo-app), Limbowatch reported **16 advisories in 6 packages**. **Dependabot alerts and OSV-Scanner reported none of them.** All 16 were rechecked against primary sources on 2026-11-07:
- each is a published, not-withdrawn advisory in the maintainer's own repository;
- each names the package, and covers the installed version by that ecosystem's own version rules;
- each has a released fix;
- none is in GitHub's reviewed database or in OSV.

## Setup

[`limbowatch/demo-app`](https://github.com/limbowatch/demo-app) is a test project, not a real application. Its four services have lockfiles generated by the package managers themselves:

| Directory | Lockfile | Generated with |
|---|---|---|
| `web/` | `package-lock.json` (71 packages) | `npm install --package-lock-only` |
| `api/` | `go.mod`, `go.sum` | `go mod tidy` |
| `worker/` | `requirements.txt` | written by hand, pinned |
| `billing/` | `Gemfile.lock` | `bundle lock` in `ruby:3.4-slim` |

**The versions were chosen on purpose.** I picked them from the [limbo feed](https://limbo.watch/feed/) on 2026-11-06 so that some are affected. This demo shows that the findings are real and that other tools miss them. It does not show how common they are. For how common, see [real projects](#in-real-projects) below.

## Results

| Tool, same tree | Findings for these 16 advisories |
|---|---|
| Limbowatch `scan` (CLI, GitLab CI component, GitHub action) | **16** |
| GitHub Dependabot alerts (public repo, dependency graph built) | **0**, and 0 alerts in total |
| OSV-Scanner 2.7.0, online (`scan source -r .`) | **0** (it reported 6 other, already-reviewed vulnerabilities in transitive dependencies) |

How the findings show up in CI:
- **GitLab merge request** adding `scapy==2.7.0`: "Code Quality scans found **51 new findings**". That's scapy's 51 advisories in limbo.
- **GitHub [pull request](https://github.com/limbowatch/demo-app/pull/1)** with the same change: code scanning reports "**51 new alerts** including 4 high severity", inline on the added line.

## How each finding was checked

Everything was checked on 2026-11-07 against primary sources, without Limbowatch's own code. [`verify.py`](verify.py) reruns the API checks and writes [`evidence.json`](evidence.json).

1. **The advisory is real.**
   - Check: `GET /repos/{owner}/{repo}/security-advisories/{ghsa}`.
   - Result: all 16 have state `published` and no `withdrawn_at`, each in the upstream's own repository, and each lists the package.
2. **The installed version is affected.** Each version was checked against the maintainer's range with that ecosystem's own version library:

   | Ecosystem | Library |
   |---|---|
   | npm | `semver` |
   | PyPI | `packaging.specifiers` |
   | RubyGems | `Gem::Requirement` |
   | Go | `golang.org/x/mod/semver` |

   Result: every installed version is in range, and every fixed version is outside it.
3. **A fix exists.** Every fixed version is published in its registry: undici 7.30.2, dnspython 2.9.2, rack 2.2.25, nokogiri 1.19.5, pgx v5.12.0, chi v5.5.0.
4. **Scanners can't see it.**
   - Checks:
     - `GET /advisories/{ghsa}` (GitHub's reviewed database);
     - `GET /advisories?type=reviewed&cve_id=…` for each cited CVE;
     - OSV: `GET /v1/vulns/{ghsa}` and `POST /v1/query` by package and version.
   - Result: all four checks come back empty for every finding (404 from both by-ID lookups).
   - chi's uncited CVE, from VulnCheck, is in OSV only as a record tied to git commits, with no package name. Package-based scanners don't match it.
5. **Dependabot sees the packages, but has nothing to match.**
   - Check: the repo's dependency graph lists undici, rack, nokogiri, pgx, chi and dnspython at these versions.
   - Result: GitHub's reviewed database has no active advisory for them, so Dependabot raised 0 alerts. (`affects=express@5.1.0` returns one advisory, but it was withdrawn in December 2025.)

## In real projects

The demo shows the mechanism. Prevalence comes from real projects and the live tracker:
- **The October report's 15 popular projects,** at their October commits (2026-11-05, [FINDINGS F-085](../../docs/FINDINGS.md#f-085)):
  - **269 affected package-versions in 13 of 14 readable projects**, GitLab alone 125, that scanners reading GitHub's database or OSV report as clean;
  - of 657 findings checked live, none was contradicted.
- **The live tracker** ([limbo.watch](https://limbo.watch), 2026-11-07):
  - 8,803 advisories in limbo, 4,347 of them critical or high;
  - median wait so far 57 days, and 2,844 waiting more than 3 months.

## Limits

- **It's a head start, not a permanent difference.** Most of these advisories will be reviewed, and then Dependabot and OSV-Scanner report them. Limbowatch reports that change as "now visible to scanners".
- **Ranges haven't been reviewed.** They are as entered by maintainers. When a range contradicts its own fix, Limbowatch reports the finding as possible, not certain.
- **GitLab's own Dependency Scanning wasn't compared.** It reads the GitLab Advisory Database, which this project doesn't query.
- **The offline inventory doesn't resolve transitive Python dependencies.** It reads only what `requirements.txt` lists, so `certifi` and `idna` weren't checked. OSV-Scanner resolves those online.
